# Opt-in reporting after a capped native response

The corrected Sarvam comparison exposed a specific integration gap. One native response returned HTTP 200 with `finish_reason=length`, an 8,192-token completion, no content and no tool calls. The original validator stopped before either final reporter ran. The original episode remains failed; this implementation does not modify or regrade it.

`benchmarks.sarvam_reporting_handoff.prepare_plan` prepares the existing two no-tools reporting requests from the last verified history. The capped message is preserved in a local failure sidecar and never inserted as source evidence. The helper accepts only an exact known cap with no tool calls, known usage, matching request/model/job, a caller-owned matching scope, unchanged backend state, and complete linked prior read receipts. It refuses prior writes, uncertain backend effects, malformed or pending tool calls, duplicate JSON keys, unknown source fields and evaluator labels. This bounded implementation does not attempt recovery after an uncertain write.

`dispatch_once` accepts an injected reporting dispatcher; it has no API-key reader or provider transport. It creates an exclusive claim file and syncs the file and its directory before either call. The claim stays after failure, and both jobs are claimed before dispatch. Reusing that stable path prevents automatic replay even with a new in-memory ledger. No actor or tool is retried. At most three native calls and two reporter calls fit the existing five-call allowance; the original failed call remains part of that accounting.

Execution status is projected from the same actual receipts and trusted intent. The answer and clarification flag are never repaired. Tests check that property alongside capped/uncertain outcomes, cross-scope state, source contamination, missing receipts, plan mutation and repeat dispatch. The exact saved capped episode prepares successfully offline without making a new call.

The caller must authenticate supplied artifacts and identity, provide stable claim storage, and enforce the actual monetary budget in its dispatcher. Hashes link records but do not authenticate a server. This helper is opt-in research code, not a default production recovery policy. Its tests prove routing and rejection behavior; they do not prove a recovered answer, an accuracy gain or a memory advantage. A new frozen prospective comparison is required before live promotion.
