# Opt-in Sarvam evidence views

`benchmarks/sarvam_evidence_views.py` prepares an alternate **final reporting input** from an already completed ordinary episode. It does not run the actor, call a model, read a credential, execute a tool, score an answer, or change the receipt-owned application status.

Call `request_for(original_final_request, actual_tool_trace)` after the existing ordinary engine has produced its no-tools final request. The returned request keeps the same model, system instruction, schema, temperature, reasoning profile and token cap. Only the user evidence JSON is reorganized. The module is not wired into the frozen comparison or selected as a default.

The `source_view` contains the exact question and ordered original source utterances. It does **not** promote a customer's report of availability into a server-verified inventory fact. The `execution_view` contains the original scoped application evidence and tool messages only after they match the application-owned trace. `actor_claims` keeps each complete native assistant message, including any reasoning fields, separately and labels it `actor_claim_only`. `protocol_context` retains the original actor system message and tool definitions. The model request contains every original value once in grouped form, with hashes and indexes showing order and provenance. `reconstruct()` verifies that the grouped request recreates the exact original JSON transcript and that actor and receipt groups retain their roles. Given the caller's actual tool trace, it also verifies receipt linkage and the trace hash; without that argument, the hash is preserved but cannot attest a trace. The full original transcript is also returned as a local `audit` sidecar by `from_final_request()` and excluded from `request_for()`'s model payload.

The transformer rejects unexpected runtime fields such as gold labels, request/approval/prior-receipt booking-scope mismatches, duplicate source IDs or JSON keys, orphan or altered tool messages, and an extra or missing actual trace event. Its trust boundary begins at the caller: the application must authenticate the customer, supply the original final request and actual trace, and attest that `application_evidence` came from its backend. The trace is caller-owned, not cryptographically authenticated by this module. Hashes detect transformation drift; they are not signatures or independent proof of backend origin. The original user envelope must be canonical JSON so its exact text can be reconstructed without duplicating it in the model request. A source utterance can mention a different booking legitimately, so the module preserves that text rather than guessing its semantic target.

The complete actor claims remain visible to the later reporter in a separate view. This preserves coverage but means the layout alone cannot guarantee that a model will ignore a wrong actor statement. A future actor-withheld ablation would need a separately frozen input policy and an external audit copy, with the information difference disclosed. The current module deliberately makes no date or clarification decision. In particular, unknown slot availability stays unknown to this code even when `read_current` returns a booking date.

Offline tests check lossless reconstruction and coverage, profile preservation, Telugu source text, complete actor fields, claim/receipt separation, condition text changes, scope and label refusal, and receipt tampering. A read-only replay against all 32 saved control final requests from the stopped fresh confirmation also validates compatibility with actual histories. Grouping changes prompt token count and possibly model attention; a later fixed-model comparison must measure token length and actual cost along with accuracy. No accuracy or cost benefit is measured here.

## Bounded comparison harness

`benchmarks.sarvam_evidence_ablation` prepares and audits a separate three-arm, saved-history screen: original chronological evidence, lossless grouping, and the same grouping with earlier assistant prose omitted. It keeps both model profiles and the reporter instruction fixed across arms. The original actor, tool proposals and receipts are shared; the screen measures reporting effects, not new action execution or long-term memory.

Preparation requires a completed 240-episode parent audit, 480 recorded assistant reporter judgments, unambiguous selected cases, a source-only selection record, and the exact audited budget carry. The archive contains the selected parent evidence and review so its checks work after relocation. Preparation and audit are offline. Live execution requires the separate `run --allow-paid` action; a started manifest cannot be resumed or retried. Invalid or empty answers remain failures, and an infrastructure failure makes the screen incomplete.

The initial design contains 108 reporter calls from 36 model histories over 18 English/Hindi/Telugu renderings of six related scenarios. This is development research. The implementation and its mocked execution tests establish no measured accuracy benefit; actual outcomes require a separately frozen and audited run. Omission is intentionally not lossless: its ledger lists each removed nonempty assistant prose field, while all source text, tool-call proposals and actual receipts remain unchanged.

## October 13 execution decision

The corrected parent attempted all 240 native episodes, but a capped native response left both reporters unreached for a selected history. The parent also failed the no-increase requirement for wrong non-null dates in Conversations. The prospective 108-call screen remains **blocked and unexecuted**. Its selected case was not replaced and its completeness requirement was not weakened. The [report](../benchmarks/audits/sarvam-fresh-confirmation-v3-2026-10-13/REPORT.md) preserves those outcomes. No evidence-view accuracy gain is measured.
