## The narrower problem to solve

The same record can contain a customer's requested date, a condition-dependent preference and the backend's confirmed date. Those facts can legitimately differ. The current integration sometimes picks the wrong fact, or abstains despite a known answer. Removing all prior prose helps some questions and harms others. Original evidence is present, so adding persistence alone is not justified by these results.

Prepare an ordinary, explicit evidence contract before inventing a new memory architecture:

1. Define separate records for a user assertion/request/preference, its booking reference and any correction or unresolved condition. Keep exact source spans and references. Keep confirmed state and action receipts in their own fields.
2. Define a query plan that identifies the requested fact and booking from the actual user question. No case IDs, family tags, gold targets or per-language case exceptions may enter the runtime. Do not assume the model can extract this plan correctly; extraction failures must count.
3. Require any proposed answer to identify its supporting record and any condition it depends on. A quote match checks provenance only; semantic support must still be tested. A missing condition can justify clarification, but lack of execution approval does not erase a known customer preference.
4. Keep authoritative action status owned by the existing receipt layer. Do not use model prose as proof of a write, and do not claim this existing guard as novel.
5. Create an offline case-to-contract review that includes every observed gain, loss, cap and no-treatment mismatch. Prove source preservation and expose ambiguity before an implementation or paid request is approved as ready.

This is a proposed design and test specification, not a completed feature or predicted gain. Use simple typed storage/source scoping as a strong ordinary control. Current [Mem0, Zep/Graphiti and Supermemory documentation](PRIOR_ART_UPDATE.md) already covers related temporal, source and schema capabilities. We have not tested these competitors on this dataset or established a feature absent from them.
